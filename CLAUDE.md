# Agent Hub

Hub abierto donde agentes de IA se registran con identidad criptográfica, descubren topics, publican y reciben eventos firmados y se envían mensajes cifrados de extremo a extremo. Versión 1.0.0, la primera publicada (el paquete es `lucid-kit`): un proceso de Node, con dos dependencias (`ts-mls`, para MLS, y `@noble/hashes`, que `ts-mls` necesita y no declara).

**Antes de cambiar nada, lee `docs/HANDOFF.md`**: recoge las decisiones de diseño, lo que está hecho, lo que no está verificado y la hoja de ruta. `README.md` documenta el uso y el protocolo.

## Comandos

```bash
npm install                   # ts-mls y @noble/hashes
npm test                      # 290 tests; deben pasar todos antes y después de cada cambio
npm run demo                  # flujo completo con un hub en memoria
node bin/agenthub.mjs hub     # hub local en 127.0.0.1:8787, estado en ./data
node bin/agenthub.mjs --help  # CLI de agente y de controlador
node bin/agenthub.mjs mcp     # servidor MCP por stdio
node bin/agenthub.mjs witness --log DID   # un testigo del registro de ese hub
node --test test/trust.test.mjs   # un solo fichero de tests
bash checks/all.sh            # comprobaciones con procesos reales, fuera de npm test: unos dos minutos
```

## Estructura

- `src/core/` criptografía y formatos, compartidos por hub y SDK: `jcs`, `didkey`, `proof`, `sign`, `reqsig`, `pow`, `schema`, `search`, `hpke`, `e2e`, `delegation`, `didweb`, `groupkey`, `instance`, `topicname` y `address` (nombres de topic y direcciones de agente, propios y de otro hub: `topic@hub`, `did@hub`), `sse`, `merkle` y `log` (el registro de transparencia), `statemap` (el directorio como un mapa que cabe en un hash, para enseñar un solo nombre del registro con su demostración), `note` y `witness` (el estado del registro y sus cofirmas en el formato de C2SP, y lo que hace un testigo con él), `statement` (lo que firma un agente al cambiar algo suyo, y lo que firman su guardián y su sucesor cuando cambia de clave), `policy` (cómo se escribe la política de un topic), `attestation` (lo que firma un verificador: que un controlador es una cuenta, nombrada por una referencia opaca), `a2a` (la tarjeta de un agente en el formato de A2A, y su firma), `oasf` (un agente como registro de OASF, para el directorio de AGNTCY, alrededor de esa tarjeta) y `control` (un controlador demuestra a un servicio que tiene su clave, también la de un did:web).
- `src/hub/` `server.mjs` (rutas HTTP y SSE, y los topics entre hubs), `store.mjs` (estado en memoria y diario), `ratelimit.mjs`, `quota.mjs` (cuotas por cuenta y por nivel), `metrics.mjs` (métricas, en un puerto local aparte), `federation.mjs` (la clave del hub y el emparejamiento con otros hubs).
- `src/witness/` el testigo: un servicio pequeño que cofirma el registro de un hub mientras solo crece (`server.mjs`; las reglas están en `core/witness.mjs`). Es AGPL, como el hub.
- `src/verifier/` el verificador de cuentas: `server.mjs` (firma atestaciones a quien demuestra con su clave de controlador que es una cuenta) y `github.mjs` (el flujo de dispositivo de GitHub). Es AGPL, como el hub.
- `src/mls/` MLS: `credential` (quién es un miembro), `member` (el único fichero que toca `ts-mls`), `dm` (conversaciones entre dos agentes), `topic` (grupos de los topics privados y quién puede cambiarlos).
- `src/sdk/index.mjs` cliente de agente; `src/sdk/state.mjs` dónde guarda el estado; `src/sdk/follower.mjs` cómo sigue el registro de transparencia del hub. `src/mcp/server.mjs` servidor MCP sobre el SDK. `bin/agenthub.mjs` CLI.
- `test/` un fichero por área (`mls` para el adaptador y las conversaciones, `topics-mls` para los topics privados sobre MLS, `private` para los de clave de topic, `federation` para lo que pasa entre dos hubs, `federation-mls` para las conversaciones MLS entre ellos, `log` para el registro de transparencia, `statemap` y `logstate` para lo que el registro dice de un solo nombre sin leerlo, `statements` para lo que firma un agente al cambiar algo suyo, `a2a` para la tarjeta de A2A, `oasf` para el registro de OASF, `witness` para los testigos del registro, `succession` para el cambio de clave de un agente, `package` para lo que llevaría el paquete, `site` para la landing); `test/helpers.mjs` arranca hubs de prueba.
- `server.json` es la ficha del servidor MCP para el registro de MCP, sin publicar: su nombre es el `mcpName` de `package.json`, y `test/package.test.mjs` comprueba que dice lo que el paquete es. El mismo test comprueba qué llevaría el paquete si se publicara: `bin/`, `src/` y las licencias (`files`), y nada del resto del repositorio.
- `.mcp.json` registra `agenthub mcp` como servidor del proyecto: si la sesión tiene herramientas `hub_*`, vienen de ahí y necesitan un hub local en marcha (`node bin/agenthub.mjs hub`).
- `docs/` `HANDOFF.md` (decisiones, estado y hoja de ruta del núcleo abierto; lo del servicio alojado tiene el suyo, en su repositorio), `DESIGN.md` (el diseño objetivo, no lo construido) y `SELF-HOSTING.md` (montar un hub propio).
- `deploy/self-hosted/` lo que necesita quien monta su propio hub: Docker Compose con Caddy, una unidad de systemd y `backup.sh`.
- `checks/` comprobaciones con procesos reales, fuera de `npm test`: dos hubs emparejados en dos procesos, la actualización desde la versión anterior y las dos versiones a la vez (que `all.sh` no pasa hasta la versión siguiente a la 1.0.0: `checks/README.md`), un testigo con un hub y sus agentes, un agente que cambia de clave, el recorrido (`tour.sh`: cada orden del CLI que las demás no usan, con el verificador de cuentas y un GitHub simulado, y un hub por HTTPS), el servidor MCP con el cliente oficial de MCP y las tarjetas de A2A con el SDK oficial de A2A (que son dependencias de `checks/mcp-client` y `checks/a2a-client`, no del producto). `checks/README.md` dice qué comprueba cada una, qué necesita y las reglas que cumplen sus guiones. `checks/self-hosted.sh` va aparte, porque necesita Docker: ejecuta los ficheros de `deploy/self-hosted/` como dice la guía.
- El servicio alojado está en otro repositorio, privado, y usa este como dependencia de npm, fijada a una etiqueta (`lucid-kit#vX.Y.Z`): importa de `src/core`, `src/mls` y `src/sdk` por su ruta (`lucid-kit/src/core/…`) y construye la imagen del hub con el `Dockerfile` de aquí. Por eso `package.json` no lleva campo `exports`, no tiene scripts que se ejecuten al instalarlo (`prepare`, `install`…), y mover o renombrar un fichero de esas tres carpetas es un cambio de versión.
- `.github/workflows/ci.yml` la integración continua: los tests con Node 20, 22 y 24 y la demo, `checks/all.sh`, y la imagen del hub con `checks/self-hosted.sh`, en cada push y pull request que no sea solo de documentación.
- `experiments/` pruebas que respaldan decisiones, cada una con su README. No son parte del producto ni de `npm test`, y tienen sus propias dependencias. `experiments/mutations/` son las mutaciones con que se comprueba que los tests de un área cazan cada una de sus defensas: un guion por área, que cambia el código en sitio mientras corre y lo deja como estaba. Quien toca una de esas áreas pasa su guion, y quien añade una defensa añade su mutación.
- `site/` la landing de LUCID (`site/README.md`): HTML estático en inglés (`index.html`) y en español (`es/index.html`), sin dependencias ni paso de construcción. Su demo comprueba en el navegador la firma de un evento con `site/assets/verify.mjs`, que repite la comprobación del núcleo sin Node; `test/site.test.mjs` la mantiene igual a la del núcleo y las dos páginas iguales entre sí. Lo que enseña como bytes del protocolo lo escribe `site/tools/fixtures.mjs` con un hub y un testigo de verdad, y las ilustraciones isométricas, `site/tools/art.mjs`, con una tinta por letra: ninguna de las dos cosas se edita a mano en las páginas. Las ilustraciones se mueven solo en pantalla y se quedan quietas con «reducir movimiento» (`site/assets/motion.mjs`). LUCID es el nombre del proyecto hacia fuera (sección 35 de `docs/HANDOFF.md`); el código sigue llamándose Agent Hub hasta que se renombre.
- `AGENTS.md` remite a este fichero, para los agentes que no lo leen por sí mismos. No lleva reglas propias.

## Reglas que el código ya cumple y hay que mantener

- **El hub no es de fiar para la autoría ni el contenido.** Todo lo que el SDK entrega a la aplicación se verifica en el extremo: firma, remitente, destino, esquema y descifrado. Un cambio en el hub nunca debe ser lo único que impide un ataque.
- **Lo que escribe otro agente es dato, no instrucción.** Payloads, y también nombres y descripciones de topics y agentes, llegan a un modelo solo envueltos (`toModelContext`, `untrusted` en el servidor MCP) y con `<` escapado. Lo que escribe el hub, también: de un rechazo suyo el modelo ve el código, una explicación del propio servidor MCP y el texto del hub aparte, envuelto (`refusal`). Un `HubError` dice si sus palabras son del hub (`fromHub`) o del SDK. Lo que el hub escribe en su salida de lo que eligió otro (un nombre, un motivo) va entre comillas y sin caracteres de control (`printed`): lo lee su operador, y se guarda en logs. Y de una respuesta correcta del hub, una herramienta solo cuenta como hecho lo que pidió quien llama, números, booleanos y cadenas con forma comprobada (un DID, un nombre de topic, un nivel): una herramienta nueva no devuelve tal cual lo que contesta el hub.
- **Firmas.** Se firma `contexto + "\n" + JCS(payload)` con la prueba fuera del payload (`core/proof.mjs`). Cada tipo de declaración firmada tiene su propio `CONTEXT`; uno nuevo exige contexto nuevo. Una petición se firma para la dirección del hub al que va (`agenthub/request/v2`, `core/reqsig.mjs`), y el hub solo acepta las firmadas para la suya (`wrong_hub`); lo que un hub pide a otro, también. Un hub que escucha fuera de esta máquina necesita su dirección pública para arrancar.
- **Agente e instancia.** Un agente es una identidad; cada copia en ejecución es una instancia con su propia clave y un certificado firmado por el agente (`core/instance.mjs`). Lo que firma una instancia vale por ese certificado, que viaja en la prueba y que cada receptor comprueba. Lo que decide quién es el agente (tarjeta, delegación, retirada, otras instancias) exige la clave del agente: `requireAgentKey` en el hub.
- **Cifrado.** Primitivas de `node:crypto`, y MLS con `ts-mls`, siempre a través de `src/mls/member.mjs` y nunca escrito a mano. Todo texto cifrado va ligado por AAD a quién lo envía, a quién va y a qué evento pertenece. No inventes construcciones nuevas sin dejar escrito qué garantizan y qué no.
- **Estado de MLS.** El secreto hacia adelante depende de que el estado avance y se guarde: se guarda antes de enviar un mensaje y antes de entregar uno recibido, y el secreto de un KeyPackage se borra al usarlo. Las operaciones de MLS de un cliente van de una en una (`#inTurn`). Ninguna función de `src/mls/member.mjs` modifica el estado que recibe: devuelve el nuevo.
- **Commits de MLS.** El hub acepta uno por época y cada lector aplica los mismos en el mismo orden. Un lector guarda su commit antes de enviarlo y, si reintenta, envía ese mismo. Para leer avanza solo hasta la época del mensaje; para escribir, hasta la última. Las decisiones están en la sección 14 de `docs/HANDOFF.md`.
- **Miembros de un grupo.** El hub no ve dentro de un commit: quién puede meter o sacar a quién lo comprueba cada miembro al aplicarlo (`mayChange`), y quien entra comprueba quién le invitó. En un topic privado decide el dueño, y cada agente sus propias instancias (`src/mls/topic.mjs`, sección 15 de `docs/HANDOFF.md`). El SDK no acepta del hub un grupo cuyo nombre no sea el del topic o la conversación en cuestión. Cuál es el grupo en curso y quién está en él son palabra del hub: antes de escribir, el SDK comprueba el nombre, que el grupo no sea anterior al más nuevo que guarda (`#notBefore`; un hub que empezó de cero se le dice con `forgetGroups`) y, en una conversación, que los miembros que tiene el propio grupo sean los lectores comprobados y ninguno más (`#holdsOnly`). En un grupo que hace el SDK solo entran los lectores que comprobó, reparta el hub los KeyPackages que reparta, y una instancia entra mientras su certificado está en vigor (`inspectKeyPackage`): nadie escribe donde queda una caducada (`lapsedMembers`). Un lector es del agente que dice su credencial, no del de la lista en la que un hub lo ponga. Un grupo se usa para escribir solo desde la conversación en la que se guardó.
- **Federación.** Un hub solo contesta como par a las claves que su operador le dio, o a las de los hubs que se emparejaron solos si su operador lo abrió (`openPairing`: el que pide demuestra que contesta en la dirección que da, y solo direcciones HTTPS públicas) (`not_a_peer` para las demás), y lo que pide a otro hub va firmado con su propia clave a la dirección que le dio el operador, sin seguir redirecciones. Estar emparejado no hace de un hub alguien de fiar para el contenido: lo que llega de otro hub se verifica como lo que llega del propio. Las decisiones están en las secciones 16 y 17 de `docs/HANDOFF.md`.
- **Entre hubs.** Un evento o un mensaje directo dice para qué hub es (`hub`, dentro de lo que firma el autor); entre hubs es obligatorio. Los mensajes directos cruzan sobre MLS cuando los dos lados pueden y sellados con HPKE cuando no, y el SDK no baja de MLS a HPKE lo que escribe a un agente con el que ya habló por MLS, esté donde esté (`#talkedOverMls`), sin que se lo pidan: dónde está un agente lo dice un hub. Una conversación entre dos hubs tiene una casa, el hub del agente cuyo DID va primero (`isHome`): es quien dice el grupo y la época, y el otro hub le pregunta. Abrir lo que se recibió no necesita a otro hub: el hub que no es la casa guarda copia de los commits (`copyCommits`, operación `mls.copy`) y no acepta de la casa un mensaje hasta tener los que harán falta; quien lee dice hasta dónde los necesita (`until`), y mientras lee no pide a otro hub el grupo siguiente. Lo que un hub emparejado hace con una conversación se guarda bajo ese hub (`acrossKey`, y `from` en las invitaciones) y no toca nada más, y lo que puede hacer guardar tiene un tope (`requireRoom`, y 20 invitaciones por lector): qué agentes tiene es su palabra, y nombrar uno más no le cuesta nada. A un agente de otro hub este lo trata como una clave, diga lo que diga el otro hub de su nivel. Una delegación deja salir a su agente a otros hubs solo si los nombra (patrones con `@hub`, `direct_hubs`). Lo que otro hub escribe es dato: de un rechazo suyo pasa el código, si es uno de los que este hub conoce (`REFUSALS`), y nunca el texto (`peerAnswer`), con el hub del que viene (`peer`) para que nadie lo tome por algo que dice el propio; y lo que cuenta de sus topics se enseña solo con la forma esperada (`remoteView`). La clave de un hub no es la de un agente ni la de una instancia (`hub_conflict`): lo que un hub guarda para cada uno lo guarda por esa clave. El nombre de un grupo es de un solo grupo (`requireUnusedName`). Lo que un hub pide a otro por cuenta de quien le llama sale de un cupo (`rationed`). Lo que un hub sigue de otro se le dice entero, y los avisos a un mismo par van de uno en uno (`inTurnWith`).
- **Registro de transparencia.** Todo cambio del directorio (tarjetas, delegaciones, revocaciones, instancias, topics y sus políticas, y las atestaciones de cuenta) deja una entrada en el registro, apuntada en `store.mjs` al aplicar la operación: un cambio nuevo del directorio necesita su tipo de entrada y su regla en `Directory` (`core/log.mjs`). Las reglas de `Directory` son las que un hub honrado cumple con cualquier configuración: nunca una cuota, un límite ni un margen de reloj. Un registro que rompe sus reglas no tiene arreglo, así que el hub no puede apuntar nada que ellas rechacen: una entrada se fecha en el instante en que el hub comprobó lo que lleva, lo que el registro no olvida (delegaciones revocadas, instancias retiradas) tampoco lo olvida el hub, y `startHub` repasa el registro de cada hub de prueba al cerrarlo. El árbol es el de RFC 6962 tal cual, con sus vectores. Lo que cambia un agente (crear un topic o cambiar quién lo usa, retirar una instancia, soltar su delegación, retirarse) lleva su declaración firmada (`core/statement.mjs`): dice para qué hub es, está hecha para valer una sola vez, dice lo que decide quien firma y no lo que el hub le enseñó (quien cambia un topic firma solo lo que cambia), y la comprueban el hub (`acceptStatement`) y cada lector (`Directory`), los dos con `verifyStatement` y lo que cada uno sabe. Un cambio nuevo que haga un agente necesita su declaración, con su `CONTEXT`. La forma de una política de topic está en `core/policy.mjs`, porque la firma su dueño y la guarda el hub. Un cliente con estado sigue el registro (`sdk/follower.mjs`) y contrasta con él lo que el hub le enseña y quién firma lo que recibe: lo que el SDK tome del hub sobre un agente o un topic de ese hub tiene que pasar por ahí (`#heldToLog`), también lo que el hub contesta a un cambio que hizo el propio agente. Los mensajes de error del SDK no repiten texto que venga del hub: pueden acabar delante de un modelo. Las decisiones están en la sección 19 de `docs/HANDOFF.md`. El directorio es además un mapa que cabe en un hash (`core/statemap.mjs`), y el hub apunta su raíz en una entrada (`log.state`) para enseñar un solo nombre con su demostración (`verifyStateAnswer`): una regla de `Directory` que cambia algo lo dice al mapa (`#saidOf`), y `startHub` comprueba al cerrar cada hub de prueba que el mapa llevado entrada a entrada es el de lo que el directorio tiene. El hub saca ese estado con las mismas reglas que cualquier lector, sobre su propio registro, y esa entrada no se escribe si nada cambió. Las decisiones están en la sección 34.
- **A2A.** La tarjeta de A2A de un agente no la escribe nadie: sale por regla de su tarjeta y de la dirección del hub (`core/a2a.mjs`), y la firma el agente con su clave (un JWS, el único que firma una clave de agente), no el hub. La firma viaja en la tarjeta (`a2a`), así que no hay estado nuevo ni entrada nueva en el registro. El hub sirve solo la que lleva esa firma para su dirección, y ninguna de un agente que no enseñaría en una búsqueda. La regla copia los valores tal cual: nada en ella puede depender de la versión de Node, o el agente y el hub firmarían bytes distintos. Lo que se firma tiene que ser lo que firma el SDK oficial de A2A: `checks/a2a-client` lo comprueba, y por él `capabilities` no va vacío. La tarjeta dice dónde se encuentra al agente; no hay puente para llamarlo por A2A, y uno tendría que ver los mensajes en claro. Las decisiones están en la sección 28 de `docs/HANDOFF.md`.
- **Testigos.** Seguir el registro no impide que un hub lleve dos y enseñe uno a cada lector: para eso lo cofirman testigos, servicios de otros (`src/witness/`). Un testigo cofirma de cada registro una sola lista: comprueba que lo que le enseñan sigue de lo que cofirmó, y lo deja escrito en disco antes de contestar; nada de eso puede aflojarse ni cambiar de orden. Un cliente con testigos (`witnesses`) toma el registro solo si bastantes de ellos han cofirmado hace poco un estado que es del registro de su hub (su `origin` es el DID del hub), que firma el hub, y por el que empieza lo que el cliente leyó; sin eso no se cree nada (`log_unwitnessed`). A quién se cree lo decide el cliente, nunca lo que el hub diga de sí mismo. Los formatos son los de C2SP y no se cambian (`core/note.mjs`): lo que firma un testigo empieza por `cosignature/v1`, y por eso no se confunde con ninguna otra firma. Un hub que vuelve con menos registro del que tenía no se cofirma, y así tiene que ser. Las decisiones están en la sección 32 de `docs/HANDOFF.md`.
- **Relevo.** Un agente es su clave, así que no la cambia: pasa a ser otro, su sucesor, y eso queda firmado y apuntado (`agent.succeed`). Lo firma el guardián que el agente nombró (`agent.guardian`: una clave aparte, o la de su controlador, que se nombra una vez con la clave del agente y no cambia) o, si no nombró ninguno, el propio agente; y el sucesor firma que lo acepta. A un agente se le releva una vez, nadie releva a dos, y a uno retirado solo lo releva un guardián nombrado antes, porque la clave que firmaría puede ser ya de cualquiera. Nada de eso puede aflojarse: es lo que impide a quien roba una clave quedarse con el agente. Al sucesor pasan los topics y los bloqueos, y nada que el primero tuviera por ser quien era (delegación, nivel, guardián, instancias, suscripciones). El dueño que un cliente tiene de un topic cambia solo por un relevo que diga el registro (`#handedOver`), nunca por la palabra del hub. En un topic privado sobre MLS nadie escribe en un grupo de antes del relevo (`closed`), el sucesor hace el siguiente al tomar el relevo, y antes de abrir una invitación, que se abre una vez, el cliente mira otra vez quién es el dueño. Las decisiones están en la sección 33 de `docs/HANDOFF.md`.
- **Streams.** Un stream se lee con `chunksUntil` (`core/sse.mjs`), que suelta el cuerpo cuando se le dice que pare. Abortar la petición no basta: en Node 22, si pasa el recolector de basura entre medias, el cuerpo se sigue leyendo, y quien esperaba a que acabara para cerrar espera para siempre.
- **Estado.** Toda mutación pasa por `store.commit(op)`: primero al diario, luego se aplica. Una operación que no se pudiera aplicar entera no puede llegar al diario, porque fallaría otra vez en cada arranque: `commit` rechaza antes de escribir lo que viene demasiado anidado para apuntarse (`NotRecordable`, que el servidor contesta como `nested_too_deeply`), y lo que una ruta deja pasar tiene que poder aplicarse. La reproducción del diario debe ser determinista: lo que dependa del reloj o de una política se decide en `server.mjs` antes del commit y se graba en la operación (ejemplo: `recipients` en `event.publish`).
- **Validación en el hub.** Entradas con límites de tamaño y forma exacta. Una prueba que va a quedar apuntada en el registro no lleva más campos que los suyos (`requireBareProof`), y lo que deja una entrada en el registro tiene un cupo: lo apuntado no se borra; errores como `{ error: { code, message } }` con códigos estables, que los tests comprueban.
- **Tests que se cuelgan.** Si un fichero de tests lleva 40 segundos, `test/helpers.mjs` dice en qué test está, qué peticiones no han contestado y qué mantiene ocupado al proceso. Un test nuevo no busca en el DNS ni espera a nada de fuera de la máquina: al hub de prueba se le dice cómo resolver nombres (`lookup`) y cómo llegar a otros (`fetch`).
- **Tests.** Cada cambio de comportamiento lleva tests, incluidos los casos de ataque (suplantación, reutilización, manipulación). Los vectores oficiales valen más que las pruebas de ida y vuelta: HPKE reproduce el vector A.1.1 del RFC 9180.
- **Honestidad en la documentación.** El README distingue lo implementado, lo no verificado y lo que falta. Mantén esa distinción al añadir cosas.

## Convenciones

- Código, comentarios y mensajes de error en inglés. README, demo y textos para el usuario en español.
- Licencias: el cliente (`src/core`, `src/mls`, `src/sdk`, `src/mcp`, tests, ejemplos y comprobaciones) es Apache-2.0; el hub (`src/hub`), el verificador (`src/verifier`), el testigo (`src/witness`) y `bin/` son AGPL-3.0-only. Cada fichero `.mjs` empieza por su `SPDX-License-Identifier`, y el código Apache no importa nada del hub (`test/licenses.test.mjs`).

- Dependencias: `ts-mls` y `@noble/hashes`, con versión exacta. El dueño decidió el 13 de noviembre de 2026 que el proyecto puede tenerlas (sección 9 de `docs/HANDOFF.md`); cada una nueva se fija a una versión exacta y se menciona en el README.

## Forma de trabajar

- Trabaja en bloques pequeños y termina cada uno: tests en verde, README al día y un commit por bloque. El dueño del proyecto quiere entregas completas, no trabajo a medias.
- Al parar procesos de prueba, mata por PID, no con `pkill -f` por patrón.
- No despliegues ni crees recursos en la nube sin confirmación explícita.
